所有者：`OnlineMo`。仓库：`OnlineMo/MeloX-Watch`，目前保持私有。应用仍处于规划阶段，没有 Android 实现、APK 或设备测试结果。终审后本文规定目标治理/发布协议；CI-01–04尚未实现，现有单阶段Owner release不得用于真实发版。本文不代表目标流程已配置并验证；实际记录见 [仓库状态](13-仓库状态.md)。

本页的“已有/尚未实现”描述以main/contribution的终审基线为准。2026-11-11只读核验：CI PR #16仍打开且未合并，相关工作流维护另在Issue #15；该分支上的实现不等于主分支流程已启用。继续建设前核对真实PR/提交和13，不覆盖进行中的工作。

## 1. 当前权限与未来保护

`main` 为验收基线，`contribution` 为开发集成分支；主题分支通过 PR 合入 contribution。不增加发布分支。只有所有者创建的 contribution → main 提升 PR 可进入验收基线，所有 PR 均由所有者人工审阅、决定合并。

仓库保持私有且只有 OnlineMo 有写权限。rulesets GET 已返回 **403**，需升级 GitHub Pro 或公开才能启用所需保护；当前没有强制分支/tag 保护。

规则可用后，main 与 contribution 都必须配置并验证：

- 所有变更必须通过 PR；必需检查为 `cloud-gate`、`pr-policy`，两者均绑定提供检查的 GitHub App（GitHub Actions），不能只匹配同名状态。
- 启用 strict：合并前必须与目标分支保持最新，并解决审阅会话。
- 禁止强制推送与删除；规则对管理员同样生效，绕过列表为空。
- 必需批准审阅数为 **0**。单人所有者无法批准自己的 PR，因此人工审阅由 OnlineMo 执行并记录，只有所有者合并；不设置管理员绕过来解决自我批准问题。

发布 tag 的规则禁止更新与删除，创建仅向有写权限的主体开放；只有 OnlineMo 和所有者手动触发发布时的临时 token 获得所需 `contents: write`，公开后也不给普通贡献者写权限。发布流程负责新 tag 的校验与创建，不能靠 tag 名称本身授权发布。

CI 本身无法阻止管理员直接推送；即使未来规则生效，所有者仍然能重新配置规则。上述保护不承诺约束有权修改仓库设置的所有者。

**已确定的后续任务：应用仓库经所有者另行批准公开后，立即完成第 6 节的保护配置与核验，不能等待用户再次提醒。** 本条是保护配置的持续要求，不是现在公开仓库或发布版本的授权。

## 2. 开发版本与可信 PR 检查

当前 `version.properties` 的 **0.0.0 / 0** 只表示应用尚未开始发布，不是永久固定值，也不要求按固定字节校验。普通构建读取版本文件，打包后核对 APK 内实际 versionName/versionCode 与本次构建的版本文件一致。

**普通贡献者 PR 禁止新增、修改、删除、重命名 `version.properties`；OnlineMo 可以提出版本 PR。** 新版本提案校验规范 `x.y.z`、无 `v`/后缀/前导零，versionName/code都大于目标分支和已发布历史；code不超过项目上限2100000000。当前脚本已经检查这些项，但自动code与回同步的一致性需要CI-04补齐。

CI-04的补充要求：提案code不得超过按该head完整可达提交数加1、历史最高code加1计算出的候选上界；通过读取Git对象而不执行head源码核验，避免主分支手填巨大值却发布较小code。发布准备仍按冻结main源提交自动计算，拒绝小于已准备code的结果，不能静默覆盖为更低值。

包含版本提案的PR及main提升/回同步采用保留祖先历史的merge commit，不使用squash/rebase丢弃提案计数依据；普通不改版本的主题PR可按现有策略合并。CI-04同时验证合并后的实际main计数与prepared code，不把PR上的估算当最终版本。目标规则尚未实施，不在本轮更改仓库合并选项。

`main`只接受所有者的contribution提升PR。保护开启后的合并可能在main产生合并提交；随后由所有者用**main→contribution同步PR**回同步，再创建下一轮功能分支。同步原样传递已审阅版本文件不分配新版本，CI-04须识别指定同仓库分支方向和精确已审阅内容，不能对同步再次要求增长，也不能用同步例外接受新版本修改。主题PR真正改变版本仍按上面的严格规则。当前这一例外未实现，建设时先修CI-04，再依赖它开展版本同步。

**所有 PR，包括所有者 PR，仍禁止新增、修改、删除或重命名 `.github/workflows/` 和 `.github/actions/` 下的文件。** 重命名检查原路径和新路径。其他治理和构建政策变更仅允许所有者提出 PR。

`Trusted PR policy` 使用 `pull_request_target`，仅从目标分支固定 base SHA 读取受信任策略，以只读 API 检查 PR 文件与提交；不 checkout、导入或执行 PR head/合并结果中的任何代码，不运行其 Gradle，不接触签名或发布 secrets。API 无法完整列举的变更必须拒绝并要求拆分。普通 PR 编译另用 `pull_request`，无 secrets。

Actions 变更通过“Actions 流程变更申请”Issue 提出。所有者审阅后，以本人认证直接在 PR 之外维护；没有专用的维护工作流。若未来保护阻止该维护，只能在必要时临时调整保护，完成后立即恢复并验证，记录 Issue、精确提交、调整理由、设置前后状态和执行结果。这是显式的维护操作，不能留下永久绕过或扩大发布 token 的用途。

这类维护需把同一已审阅workflow/action改动落实到main与contribution并分别验证，恢复保护后确认两分支这些路径一致；不能只改其中一条再期望提升PR携带差异，因为该PR仍会被“所有workflow改动禁止”规则拒绝。CI-04验收包含维护后继续提升/回同步的完整周期。普通业务改动不使用此例外。

所有提交使用本人身份及 GitHub noreply 邮箱；不使用 `Co-authored-by` 尾注、AI 作者/提交者或 AI 署名。发布快照提交也使用 OnlineMo 与其 noreply 身份。

## 3. 目标发布流程：只创建快照 tag

**终审修改：先准备候选、后验收、再发布同一产物。** 当前`release.yml/release.py`是“全部门槛→构建→立即发布”，不能满足首次候选验证和同包发布；须先完成09/20中的CI-02/03，不能提前把门槛勾true来绕过。网页操作仍不需要本地编译或开启电脑，但实机验收是人工步骤，不会被Action自动完成。

### 3.1 准备候选（不发布）

OnlineMo在main的网页入口选择未来`prepare-candidate`，输入versionName和prerelease。校验actor/triggering_actor/repository/ref和基础构建条件，不要求最终设备报告、公开保护或发版批准；有权准备候选不等于获准发布。

冻结当时main为`source_sha`。完整获取其可达历史及正式`vX.Y.Z`标签，拒绝浅克隆、无效/重复/不完整版本数据。版本名高于发布历史且不低于main准备值；首个公开版0.1.0必须prerelease。设`N=rev-list --count source_sha`、`R=历史最高已发布code（无则0）`，计算`versionCode=max(N+1,R+1)`并检查上限。`+1`只包含本次版本快照提交，不包含之后的验收报告提交。

从source创建detached快照，仅改`version.properties`，父提交固定为source；不新建发布分支、不回写main/contribution。按09隔离编译和签名，保存完整快照Git对象、已正式签名APK、manifest、校验和。核对快照可达提交数确为N+1；source/snapshot/code/哈希一经验收不得改变。未发布候选可作废，后续重建必须使用新candidate ID并重新验收，不能用旧报告代替。

### 3.2 验收记录与源码冻结

候选ID由可信run ID、attempt和artifact ID共同确定。使用该APK实机验证，在`docs/releases/<version>/`保存脱敏设备/性能/视觉报告及候选验收记录；记录模板见 [候选发布验收记录](templates/候选发布验收记录.md)。报告包含candidate ID、source/snapshot、APK/证书SHA-256、versionName/code及结果，不能只写“最近一次构建通过”。

报告和`.ci/release-readiness.json`可在候选之后走文档PR合入main，形成`approval_sha`；**它不作为重新编译源，也不重新计算已冻结code**。CI-03必须证明source是approval的祖先，且其间只改变约定的`docs/releases/<version>/`报告、`docs/13-仓库状态.md`状态记录及readiness文件；这些路径不得作为应用构建输入。应用代码、依赖/工具链、版本、工作流/CI策略、证书指纹或其他文件变化都会使候选失效，须重新准备/验收。发布期间暂停其他集成，避免冻结窗口拖长；之后再恢复正常开发。

未修改任何构建输入但签名/优化产物发生改变，也视为新候选。诊断包可辅助分析，公开APK必须与正式候选验收所用哈希一致。

### 3.3 发布已验候选

OnlineMo单独批准后在网页选择未来`publish-candidate`，指定候选ID及验收记录。流程使用当前main受信任发布逻辑，读取并核对已提交记录、全部功能门槛、GOV-PUBLIC-01与真实owner授权；从可信同仓库候选run取产物和Git对象，验证来源、模式、成功结论、精确哈希/签名/包名/版本。

发布步骤**不运行Gradle、不重新创建版本commit、不重签APK**。发布锁覆盖准备/发布/恢复，避免同版本并发；再次获取最新发布历史，确认版本名/code仍大于所有已发布值。若另一候选已发布导致本候选落后，拒绝发布并重新准备，不自动改code后继续用旧验收。

仅发布job授予短期`GITHUB_TOKEN`内容写权限：推送指向原snapshot的全新不可变tag，创建draft Release，上传已验APK/manifest/SHA256SUMS及说明，核对完整后取消draft。仓库可见性由所有者单独授权；workflow不自动公开。整个流程不推送任何开发分支，不需要长期仓库写入密钥。

发布另附非敏感`publication-record.json`，记录approval SHA、原候选ID/快照/哈希、设备报告路径及批准时间；候选manifest保持原字节不改。tag源码包含候选时的状态，后续报告在approval提交中，通过该记录追溯，不谎称报告本来就在被构建快照里。

### 3.4 中断恢复

CI-03的恢复操作必须幂等：tag不存在时按上述流程创建；tag已存在且正好指向候选snapshot时可继续同一个draft/Release，逐项校验已有附件，只有缺失附件可补传。tag指向别处、同名附件不同哈希、来源记录不符一律停止，不覆盖、不删tag、不重编译。

候选artifact过期/损坏且没有可校验备份时，记录该版本发布失败，不用另一份包填充相同tag；只有找回原候选包才可恢复，否则选择新的更高版本重新验收。正式发布后禁止替换资产，修复使用新版本。

### 3.5 手表与手机配套的同候选交付

LP-14纳入首版后，本文“候选APK/同包”适用于必需APK集合中的每一个包。手表与手机应用从同一snapshot读取同一版本文件，manifest分别列角色、精确包名、哈希和证书；详见09第7节。候选验收绑定这组包及协议版本，首版公开需F-001～128全部通过，不能先发布缺少手机配套功能的较小范围版本。

prepare-candidate需要生成完整候选集；publish-candidate只上传该集合中已验过的原字节。恢复也逐包比对，只补缺失资产，不替换已存在的不同字节。两端正式包均使用已固定的项目Release证书，可信Debug使用已有Debug证书；所有者发版、禁贡献者改版本、禁止PR改workflow的规则完全相同。LP-14负责配套扩充CI实现，当前只增加此契约。

## 4. 签名、secrets 与私有恢复

已生成相互独立的 Release/Debug 证书，均使用 RSA 3072 位、SHA-256 签名、30 年有效期。证书主题分别为 `CN=OnlineMo MeloX Watch Release` 与 `CN=OnlineMo MeloX Watch Debug`，共同使用 `O=OnlineMo`、`OU=MeloX Watch`，不含 C、ST、L 或 email。公开指纹固定在 [签名证书指纹](../.ci/signing-certificates.json)，未来可信 Debug/Release APK 必须分别匹配对应指纹；不复用上游密钥。

| 仓库级 Actions secret | 用途 | 使用边界 |
| --- | --- | --- |
| `CI_DEBUG_KEYSTORE_B64` / `CI_DEBUG_STORE_PASSWORD` | 可信分支 Debug APK 的稳定签名 | 仅受信任分支；PR 不可用 |
| `RELEASE_KEYSTORE_B64` / `RELEASE_STORE_PASSWORD` | Release APK 签名，alias 为 `melox-release` | 仅所有者在 main 授权的发布流程 |

按仓库级 secrets 设计；当前私有仓库套餐下 environments 可能不受支持，不依赖 environment 审批或 environment secrets。上述是用途约定，不能据此声称 secrets 已配置完成；实际启用与验证以 [仓库状态](13-仓库状态.md) 为准。

可信 Debug 使用稳定的 `.dev` 包名与独立 Debug 证书；PR 仅用临时证书且不读取 secrets。普通 Debug 从版本文件读取应用版本，使用 source SHA、build SHA 和 Actions run 标识区分产物。正式包不带 `.dev`，使用独立 Release 证书。

用户已明确授权将 p12、明文密码和恢复元数据保存在**独立、永久私有的恢复仓库**。该仓库必须关闭 Actions、无协作者，只由所有者管理；主项目公开时它仍保持私有。此授权只适用于该恢复仓库，不允许把私钥、密码或恢复仓库名称/地址写入本项目、Issue、PR、公开材料、构建日志或产物。本文只描述通用恢复安排。签名恢复应单独验证；证书已生成、指纹已固定不代表云端 secrets 或恢复验证已完成。

### 两个分支逐一配置

网页入口为仓库 **Settings → Branches → Add classic branch protection rule**。分别建立精确匹配 `main` 和 `contribution` 的两条规则；若已经存在，检查并更新实际生效的规则，不叠加含糊的通配规则。未来 GitHub 界面变化时核对当时官方文档；也可使用等价 API，但必须读回验证，不能以请求已发送视为成功。

| 设置 | 两个分支都采用的值 |
| --- | --- |
| Branch name pattern | 一条 `main`，一条 `contribution` |
| Require a pull request before merging | 开启 |
| Require approvals / Required number of approvals | 不启用强制他人批准，API 数量为 0；唯一所有者仍需人工审阅 |
| Require review from Code Owners / Require approval of the most recent reviewable push | 不开启，避免单人仓库无法自我批准；CODEOWNERS 保留职责提示 |
| Require status checks to pass before merging | 开启；必须同时选择 `pr-policy`、`cloud-gate` |
| 状态检查来源 | 两个检查均绑定 GitHub Actions App；API 使用真实 app_id，不使用任意来源的同名状态 |
| Require branches to be up to date before merging | 开启（strict） |
| Require conversation resolution before merging | 开启 |
| Do not allow bypassing the above settings | 开启；规则对管理员同样生效，不设置永久绕过主体 |
| Allow force pushes | 关闭 |
| Allow deletions | 关闭 |

如果检查名称暂未出现在选择列表，先让正常文档 PR 运行现有两项检查，再选择真实检查；不能省略检查、伪造成功状态或用本地测试结果替代。保存每条规则后重新打开设置确认。

已约定的发布 tag 保护也须在此窗口启用并核验：`v*` 禁止更新和删除；保留所有者授权流程创建新 tag 的路径，不通过禁止所有 tag 创建使发布失效，也不新增长期写入凭据或永久绕过。

### 验收与交接

1. 分别读取 main/contribution 的实际保护配置，确认 PR 要求、两项检查及来源、strict、会话解决、管理员约束、强推/删除禁止符合上表。只看到 `protected=true` 或警告消失不足以证明全部要求已生效。
2. 用正常 PR 核实检查实际运行与合并条件；预期失败的政策验证 PR 不合并。不得向主分支尝试强推或删除来测试保护，避免配置错误时损坏真实分支。
3. 规则生效后，普通合并使用 GitHub 的 PR 合并入口或合并 API；不能通过本地快进后直接 push 来代替受保护 PR 合并。Actions 特殊维护仍按第 2 节的 Issue 流程执行，完成后立即恢复保护。
4. 在 [13 仓库状态](13-仓库状态.md) 和公开验收报告记录执行时间、操作者、两个规则/有效配置、检查 App 来源、PR/run 证据、tag 规则及恢复仓库仍私有的结果。只记录非敏感设置。
5. 全部规则确已生效并有证据，才允许所有者将 `.ci/release-readiness.json` 的 `branch_and_tag_protections` 改为 true；其他门槛和独立发版批准仍须满足。本文不提前修改该值。

任一配置/核验失败：暂停后续发布，保留失败原因与未完成项，继续修复保护；不能取消 required checks、放开管理员绕过或提前宣布首次公开发布完成。可见性已经公开不代表可以忽略保护，也不能承诺重新私有化能撤回已公开的内容。

网页配置依据为 GitHub 官方《Managing a branch protection rule》：`https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/managing-a-branch-protection-rule`。执行时复核界面与套餐实际能力，历史 403 不视为永久结论。
