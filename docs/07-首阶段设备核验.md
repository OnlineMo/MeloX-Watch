# 首阶段设备核验

**本文件是未来 P0 的操作计划，所有设备项目尚未执行。** 本次没有运行 adb、连接手表、安装应用或修改手表设置。

全部128项及256原AC按 [21 全量整合](21-本地播放器全量需求整合.md)、[覆盖矩阵](requirements/local-player-coverage.json) 和 [匿名需求基线](requirements/local-player-F001-F128.md) 执行，包括原13项待定。本文只规定探针与决策，不创建应用/测试代码，不给工期或代码规模估算。

## 1. 核验目的

核验普通 Android 智能手表应用所需的设备能力。用户当前可用的 OPPO Watch X2 圆表是主要实机测试设备，**不是产品支持范围上限**，不据此设置品牌/型号白名单。其信息仍来自用户描述，地区/固件可能影响能力；不能从名称推断 API、Wear OS 或 GMS，也不把一次实机结果推广为所有手表已测。

顺序以09/20为准：DEV-001 可先只读采集；DEV-004-A 用固定云端工具链创建一个 `:app` 最小探针并产出可追溯 APK，**先于 DEV-002/003/005**。再安装探针验证音频、登录、输入/文件入口，DEV-004-B 记录基线，P1 扩充同一工程。可信分支首个 Android 构建的 CI-01 前置仍须满足。

## 3. 未来只读采集步骤

在用户已经连接并授权调试的设备上操作。先核对序列号，避免把手机误当手表。以下 PowerShell 命令只是文档示例，尚未执行。

```powershell
adb devices -l
$watchSerial = '替换为目标手表序列号'
adb -s $watchSerial shell getprop ro.product.model
adb -s $watchSerial shell getprop ro.product.name
adb -s $watchSerial shell getprop ro.build.display.id
adb -s $watchSerial shell getprop ro.build.version.release
adb -s $watchSerial shell getprop ro.build.version.sdk
adb -s $watchSerial shell getprop ro.product.cpu.abilist
adb -s $watchSerial shell wm size
adb -s $watchSerial shell wm density
adb -s $watchSerial shell settings get system font_scale
adb -s $watchSerial shell pm list features
adb -s $watchSerial shell pm list packages com.google.android.gms
adb -s $watchSerial shell dumpsys webviewupdate
adb -s $watchSerial shell dumpsys input
adb -s $watchSerial shell df -h /data
```

`wm size/density` 在不追加数值时用于查询；本计划不修改它们。若厂商禁用命令或权限不足，记录失败并从系统“关于”和显示设置补充，不要求 root。GMS 包存在不等于服务可用，也不自动证明设备适合 Wear OS Data Layer。

网络和音频问题可在后续按需只读查看 `dumpsys connectivity`、`dumpsys audio`、`dumpsys power`，结果留在本地，记录中只保留诊断所需字段，不把包含设备/网络标识的完整输出直接发布。

## 4. 安装与运行验证（未来执行）

1. 从 DEV-004-A 云端产物核对 source/build SHA、APK 哈希、版本、精确包名与证书后安装；计划正式包名 `io.github.onlinemo.meloxwatch`，Debug 加 `.dev`。记录启动器和触摸返回，不能用本地编译包替代。
2. 在同一探针验证目标 API 和基础 Compose/Media3 组合。compile/target36、minSdk26候选按09与设备结论处理；先测试合法本地音频，再测试受控 HTTPS 音频，区分解码与网络问题。
3. 配对已有蓝牙耳机，确认实际输出；noisy 事件立即暂停，重连不自行恢复外放。分别验证两后端的唯一焦点所有者及切换时移交；ExoPlayer自动管理与公共焦点协调择一，系统MediaPlayer适配不得同时持有第二套焦点；在适用系统检查 target≥35 时顶部应用或合规前台服务条件，以及拒绝、抢占和用户暂停后旧回调不复播，详见03。
4. 熄屏并退出页面，连续播放至少 30 分钟；记录当时的电源模式、应用权限和系统设置。若只能保持亮屏才能播放，则不算通过。
5. 测试手机离线、Wi-Fi 直连、可用时蜂窝和手机代理网络，分别确认元数据请求和音频下载；不要仅依据连接图标判断。
6. 记录表冠旋转是否能进入应用、普通返回是否可用、媒体按键是否到达会话；所有主流程仍需触控可完成。另核验共用布局在方形窗口下取消圆边裁切、按实际 inset 展示；设计/模拟验证与真实方表验收分开，不新增 Wear OS 栈。
7. 调起实际系统输入法，输入中文曲名、列表名、含 `https://`、路径、`?`、`&`、`=` 和百分号编码的测试地址及曲目 ID；验证编辑、提交、取消、键盘收起与圆屏遮挡。样本不含真实 token。无可用输入或无法完成必需字段时，搜索/命名/Meting 验收保持阻断；不能以预填演示数据通过，不得以配套端输入替代手表独立搜索的正常AC；已必做的手机配套能力另按LP-14验证，不因本项失败临时扩展其授权。

本步骤涉及未来安装和测试，当前只建立清单；不提前生成、安装或执行样例。LP-14运行时分别记录手表与手机APK的source/snapshot、build SHA、run/attempt/artifact、包名/版本、APK与证书哈希；候选互通使用同一冻结快照下的实际包组合，设备能力结论绑定该组合，不能只验手表后推定手机已通过。

## 5. 登录验证记录

| 实验 | 记录内容 | 选择依据 |
| --- | --- | --- |
| 原生 QR/EAPI | 请求成功/失败、状态变化、账号校验结果、耗时；不记录原始 key/Cookie | 在目标设备上稳定可用时优先 |
| Android WebView 桥接 | provider 版本、页面加载、二维码生成、Cookie 获取及退出清理 | 只有设备存在可用 WebView 且原生路径受阻才评估 |
| 账号持久化 | 重启应用/设备、系统清理后是否保留；密钥异常处理 | 成功会话应安全保存，异常需明确重登 |
| 网络风控/限流 | HTTP/业务错误码、重试窗口、网络类型 | 有限退避，不能无限切换参数重试 |

如两条独立登录路线都失败，记录在线路径阻断原因，评审手机辅助配对或其他可行登录路径的权限与独立性；不得在计划状态下标注“扫码已支持”。已独立验证的共享基础和本地路径仍可推进，不以登录失败阻断本地工作；首版仍须在线/本地门槛全部通过，不能静默改成仅本地发布。

## 6. DEV-005：本地文件访问与格式探针（未来执行）

首个公开 `0.1.0` 已包含 P2-L 本地音乐，P0 安排探针，进入 P2-L 前必须证明至少一条面向用户的文件访问路径可行；共享 P1 可以在设备/安装/音频条件已验证后推进，不必等待另一条业务路径的阻断解除。探针使用未来云端构建的最小样例与用户允许的一次性音频样本；本次未构建、安装或运行。官方依据与完整设计见 [17 本地计划](17-本地音乐功能与实施计划.md)。

| 探针 | 操作和应留证据 | 未通过时的处理 |
| --- | --- | --- |
| 文件进入手表 | 记录用户已有文件或系统文件管理器等实际可用放置方式、可读范围与空间；内部测试音频不能冒充用户访问路径 | 无可用路径即阻断，不把未来 Wi-Fi 传歌当已解决 |
| MediaStore | 按实际 API/target 申请所需音频读取权限；查询少量已知样本，核验音频 URI、元数据、打开与播放，区分空集合/拒绝/不支持 | 拒绝保持稳定错误与旧索引；评估已经证实存在的其他授权入口 |
| 文件选择器 / SAF 树 | 核验 `ACTION_OPEN_DOCUMENT` 与 `ACTION_OPEN_DOCUMENT_TREE` 是否有处理器、能否触控选文件/树；分别记录 provider、范围和读/持久授权标志 | 无处理器就不提供该入口；不硬编码绝对路径或用 root/全盘访问绕过 |
| 父目录与 LRC | 分别测试 MediaStore、单音频 URI、树授权是否暴露可读父目录/同名 LRC；有文件选择器时再明确选择 LRC | 不暴露父目录则按授权来源分组；单音频授权不扩成目录授权，无 LRC 入口就显示无法添加/未授权 |
| 持久化与重启 | 仅在返回授权允许时获取持久 URI 读取权限；重启应用/设备后再次打开；记录 provider 对文档身份和权限的实际行为 | 临时授权不冒充持久授权；若需要持久副本且源可合法读取，单独显式导入并先检查空间 |
| 拒绝、取消、撤销与重授 | 首次拒绝/取消、扫描中撤销、播放前撤销，再从同一来源重授并重扫；旧库/收藏/列表/历史保留 | 稳定错误，限制重试；不能把失败当空扫描清库，不能要求登录来恢复本地访问 |
| 原文件移动/缺失 | 在系统文件管理器使用一次性样本模拟移动/删除，核验 URI 是否改变、是否可重新定位和重关联 | 保留身份与不可用原因；另以F-053/063/075/088真实应用入口验证获准夹具的删除、标签写回、移动及批量部分结果 |
| 必要导入副本 | 只在无法持久引用等实际需要时测试用户确认后的复制，检查独立配额/保留空间、取消及低空间 | 不自动复制整库；未完成副本不入可播库，清理临时副本不碰原件 |
| 容器＋编码矩阵 | 分别记录 MP3、AAC/ADTS、M4A 中 AAC、原生 FLAC、WAV 中 PCM、Ogg 中 Vorbis/Opus 等样本的编码/采样率/位深/声道、文件摘要与来源；测试首声/seek/时长/结束 | 成功只证明该组合；坏文件/不支持格式给稳定错误，APE/DSD所需解码方案单独审许可/ABI/资源并实测，仍禁止DRM解密 |
| 完全本地路径 | 无在线账号冷启动本地；关闭 Wi-Fi/蜂窝/手机网络代理，保持蓝牙耳机；记录本地链路无应用发起的账号/HTTP/DNS/遥测/封面歌词请求 | 系统流量不混入应用证据；已有在线播放另测，不能因进入本地页而强停；仅联网 provider 不算离线来源 |

能力结论写明“MediaStore 可用”“文件选择可用”“目录授权可用”“需要显式导入副本”各自的证据和限制，不要求固件实现所有入口，也不把某条入口失败说成已被绕过。所有支持入口都须覆盖拒绝、撤权、恢复，且至少一条能让用户实际添加并持久使用设备音频。若不存在，P0 本地门槛未通过，先记录具体能力阻断及修复/替代授权路径，不继续宣称首版可交付。

P0 的最小 30 分钟后台试验只是探针；首版仍须按 [14 性能预算](14-性能优先与资源预算.md) 完成在线至少60分钟、本地至少120分钟熄屏测试，以及06、15、16验收。实施依赖和任务状态统一引用 [05](05-开发阶段与任务清单.md)，本文件不另设工期。

## 7. 全量范围的早期探针与退出条件

初始原生Android手机方案是明确的设计选择，**手机平台确认尚未完成**；需记录目标手机API/ABI、无GMS要求、安装/签名/升级与分发渠道。F-067原文明确额外应用，F-097/124/125/126必须由真实配对客户端实现；网页只能是可选传输入口，不能替代客户端验收。只验证服务端只读接口不证明编辑能力。
