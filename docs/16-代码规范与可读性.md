**用户性能第一，视觉美观第二，可读性必须满足。** 优先保证播放可靠、控制及时、耗电可控和错误可恢复；视觉效果应在资源预算内服务操作。可读性是实现和维护的底线，不能以“性能优化”或“更短”为由取消。

## 2. 英文命名与领域词汇

源码标识符使用英文，表达业务概念；新写解释性注释默认中文。复用的上游注释、许可/版权、协议原文和官方示例保留原文，有必要再补中文理由；不为语言统一批量翻译。官方类名、API、字段和错误码保持原名。[K1]

| 对象 | 项目约定与例子 |
| --- | --- |
| package | 小写、按领域组织，如 `playback`、`lyrics`；不以 `common` 包收纳无关功能 |
| 类、接口、对象、类型别名 | `UpperCamelCase`，如 `TrackKey`、`QueueSnapshot`、`LyricsDocument` |
| 普通函数、参数、属性、局部变量 | `lowerCamelCase`；函数用动作名，如 `resolvePlaybackResource`、`restoreQueue` |
| 无返回值的 UI Composable | 使用名词性的 `UpperCamelCase`，如 `PlaybackScreen`；这是 UI 命名约定，不推广到普通业务函数 |
| 布尔值 | 表意清楚的 `isPlaying`、`hasMore`、`canRetry`，避免 `flag` 和双重否定 |
| 常量 | `const val` 使用 `UPPER_SNAKE_CASE`，如 `MAX_RETRY_ATTEMPTS`；普通 `val` 不一律大写 |
| 私有可变状态及公开只读视图 | 可使用 `_uiState` / `uiState`；下划线前缀只用于这种对应关系 |
| 文件 | 单一主类型与类型同名；相关顶层函数按职责命名，如 `LyricsParser.kt`，不用 `Utils2.kt` |
| 数值与边界 | 名字带必要单位和语义，如 `positionMs`、`cacheSizeBytes`、`pageSize`、`queueIndex`；索引起点在契约说明 |

必须沿用 03 的概念：`TrackKey` 是稳定曲目标识，`PlaybackResource` 是短期播放资源，`QueueSnapshot` 是恢复快照；`MediaSession` 与账号 `Session` 必须在使用处区分。不能用同一个 `data` 或 `item` 混指曲目、URL、下载文件和队列条目。曲目 ID 保持字符串语义，不能按标题匹配，也不能随意转为整数。

建议使用有含义的完整词；仅在极小的局部索引循环中使用 `i`。参数涉及多个同类型值、布尔选项或不同单位时，优先使用命名参数。对来自协议的秒、毫秒、页码和偏移，在适配边界转换一次，内部保持统一含义。

## 3. 格式、长度与工具状态

硬规则：遵循仓库现有 [.editorconfig](../.editorconfig)。Kotlin 使用 **4 个空格**缩进，不用 Tab；文本使用 **UTF-8、LF**，保留文件末尾换行，移除行尾空白。现有 YAML/JSON 的 2 空格例外继续按配置执行，不能把 Kotlin 规则机械套到所有格式。Kotlin 的四空格和常规大括号排版依据 [K1]。

建议将 **120 列作为初始软参考线**。长签名、调用参数和表达式按语义换行；URL、表格、协议样本等可保留完整形式。当前 `.editorconfig` 没有配置 `max_line_length`，本文不添加该配置，也不把 120 列当作已启用的自动失败条件。

硬规则：一条语句表达一个清楚的步骤，不用分号把多条语句挤在一行。禁止为追求短小而删除必要空行和注释、压成超长表达式或拆出无意义文件。格式调整保持在相关改动范围，避免让业务审查被无关重排淹没。

建议在多行声明中使用尾逗号，保持连续调用的换行和缩进一致；不要为对齐等号添加大量空格。格式工具处理空白，人工审查负责语义，二者不能互相替代。

ktlint、Detekt、Spotless 等这里只是未来候选工具，**本文没有安装、接入或验证任何 formatter/linter**。选型时必须记录准确版本、规则集、兼容性、适用路径和运行位置，再按治理流程接入；不得仅凭存在 `.editorconfig` 声称格式检查或 Android lint 已通过。

## 4. 职责、分支与最少必要抽象

硬规则：函数围绕一个可命名的责任展开，输入、结果、状态修改和失败路径能顺序读懂。参数校验与退出条件尽早表达，主体保持浅分支；遇到多层嵌套时，先区分是否混入解析、决策、存储或 UI 更新，再提取有业务名字的步骤。

建议优先使用 guard clause、明确的 `if` / `when` 和局部变量。简单、纯粹的转换可以用表达式函数或集合操作；包含网络、状态修改、重试、资源释放的流程应展开。不要为了“函数式”把有序步骤隐藏在 `map`、`fold` 或多段 Elvis 表达式里。

硬规则：禁止依靠密集链式调用、隐式接收者或嵌套 `let` / `run` / `apply` / `also` / `with` 掩盖控制流。使用 scope function 时，读者必须能立即看出操作对象和返回值；出现多个 `it` / `this`、非局部返回或隐藏副作用时，改用显式名称和普通语句。[K3]

函数和文件长度不设任意门槛，也不写行数测试；审查职责、分支和阅读成本。连续且清楚的状态转换可以较长，很多短函数相互跳转也可能更难读；不为凑数删注释、拆辅助函数或改写生成代码。

硬规则：只引入当前行为和边界需要的类型。局部变量类型明确时允许推断，公共契约、单位易混处和复杂返回值必须清楚表达类型；不能用 `Any`、字符串键字典或多层 `Pair` 逃避领域建模。

接口用于实际隔离外部协议、存储、播放边界或需要替换的依赖。03 中的仓库和解析器契约可作为这些边界；不能给每个类补一个同名接口、空用例、基类或工厂。尚未进入阶段的 `PhoneLink`、Wear OS 等保持规划，不提前制造空模块和通用框架。

## 5. 所有权、层次与播放器线程

以下均为硬规则；职责以 03 为准，拆分必须能回答“谁拥有、谁修改、谁取消、谁释放”。

| 所有者 | 应负责 | 边界与结束条件 |
| --- | --- | --- |
| UI / Composable | 展示状态、采集用户意图、维护必要的局部展示状态 | 不访问数据库或解析播放 URL，不创建播放器；可见性相关订阅、动画和计时随页面停止 |
| ViewModel | 组织页面意图、调用仓库、产生页面状态 | 不作为播放队列的第二权威；页面任务有取消边界，不持有 Activity/View 以延长其寿命 |
| Repository / 协议适配器 | 数据获取、缓存策略、错误转换、协议与领域模型映射 | 不依赖 `ui.*`，不决定导航或直接驱动 UI；一次操作向调用者暴露可取消结果 |
| 单个 Media3 播放服务 | `MediaSessionService` 持有一个 `ExoPlayer` 和对应 `MediaSession`，权威维护播放与队列 | UI 通过 `MediaController` 发送命令、观察会话；页面重建重新连接，不能复制播放器 [A2] |
| 连接与资源的创建者 | 明确 controller、listener、网络响应、流、缓存和任务的所有权 | 规定移交点、释放时机与所需线程；页面释放自己的连接，不能顺便销毁服务持有的播放器 |

服务存在不代表代码自动在后台线程运行。必须区分阻塞数据工作和播放器 API 的线程归属：

- **Player：** ExoPlayer 的访问遵守其单一 application thread；以 `player.applicationLooper` 为准。常见选择是主线程，但不能把“永远是 Main”写成通用假设；创建时选定的 Looper 和所用 Media3 组件约束必须一致。读状态、发命令、注册/移除监听及释放，均按对应 API 的线程契约执行。[A1]
- **Controller：** 调用遵守 controller 自己的 `applicationLooper`，其监听回调也有线程约定；不能因为连接到同一服务就假定与 player 是同一线程。[A3]
- **数据工作：** 网络阻塞调用、文件读写交给合适的 IO 执行环境；较重的歌词解析等 CPU 工作交给计算调度器。结果回到状态或播放器的拥有者线程后再提交，不把 `player.seekTo`、`play` 或 `release` 丢进 `Dispatchers.IO`。[A1][A4]

硬规则：异步结果回到拥有者时，必须再次校验账号、请求代次、曲目或队列版本是否仍有效。检查与状态提交在同一受控执行上下文中完成，不能检查后跨挂起点再无条件写入。

## 6. 不可变状态、意图与副作用

硬规则：对外暴露只读状态，内部变更集中到明确所有者。优先用 `val` 和不可变快照；只读 `List` 类型不等于底层内容不可变，发布后不得继续通过别名修改其列表或元素。复制或不可变集合的选择按数据规模判断，不为每次进度变化复制整条大队列。

页面按“用户意图 → 所有者处理 → 状态更新 → UI 展示”组织。播放命令交给同一会话，UI 中的加载反馈不能冒充已经播放；实际播放状态以服务为准。纯转换函数不夹带网络、日志、导航或写库，副作用放在可见的边界。

硬规则：明确区分首次加载、真实空结果、已有内容上的追加加载、可恢复错误和成功。弹窗、导航等一次性副作用必须写明生命周期重建时是否允许重放、丢失或需要确认，不能以重组次数作为触发条件。重要结果留在状态中，不能只依赖一条可能无人接收的事件。

建议先用简单的状态数据和有限的意图类型表达现有流程；只有确实能排除非法组合时再增加 sealed 类型，不为每个按钮建立一套独立框架。

## 7. 协程、取消与资源释放

硬规则：每个异步任务必须有明确 scope 所有者。页面任务使用生命周期或 ViewModel 管理的 scope；仅前台需要的二维码轮询、搜索和歌词 UI 计时还需按可见性停止，不能只等 ViewModel 销毁。音频服务持有播放所需任务，不能因页面离开被一起取消。禁止为方便使用 `GlobalScope` 或无处关闭的临时 `CoroutineScope`。[K4][A4]

一次调用内部并行工作应保持结构化并发；必须说明失败是否取消同组工作。仅当子任务确实可独立失败时使用监督语义，并分别处理结果。较长寿命任务应由显式注入的所有者接管，而非仓库偷偷启动后台任务。

硬规则：`suspend` 不自动代表后台执行或 main-safe。执行阻塞工作的层负责切换到适合的 dispatcher；已提供非阻塞挂起接口的库，按其契约调用，不机械重复切换。dispatcher 作为可替换依赖，便于调度测试；播放器调用仍遵守第 5 节的 Looper。[A4]

硬规则：取消必须向下传播并使过期工作停止。只捕获能处理的具体错误；捕获范围可能包括 `CancellationException` 时，必须原样重新抛出，不能映射为成功、空列表、普通失败提示或重试。`runCatching` 会捕获 `Throwable`，不能直接用 `getOrDefault` / `getOrElse` / `getOrNull` 把取消吞掉；挂起流程优先写清楚的 `try` / `catch`。[K5][K6]

超时也必须有语义边界：本操作自己设置的超时可以在该边界显式转换为超时结果，父任务取消仍须传播。不得捕获所有取消后统一显示“请求超时”。错误结果和用户取消的验证需分别覆盖。

硬规则：长循环在合理批次检查取消或调用可取消挂起点。取消协程并不保证底层阻塞调用、第三方回调立即停止，适配器需连接实际请求的取消能力；即使仍收到晚到结果，也不能提交到新状态。[K5]

硬规则：资源在成功、失败、取消路径都须释放，采用适合对象契约的 `use` 或 `try` / `finally`，监听器注销与连接释放应成对可查。确需挂起清理时，`NonCancellable` 仅用于有界的必要收尾，说明时间界限和原因；不能包裹完整请求、重试或整个服务来逃避取消。播放器释放还须满足其线程归属。

## 8. 重试、缓存、分页和生命周期上限

硬规则：每项持续工作都必须记录开始条件、结束条件、所有者和资源上限。配置写清单位与默认值的来源，不能留下“以后再限制”的无限增长路径。

| 场景 | 实现时必须明确的约束 |
| --- | --- |
| 请求与重试 | 单次超时、总时间预算、最大尝试次数（是否含首发）、退避上限与可重试错误；退避可取消，遵守有效的 `Retry-After`，禁止无界重试与自动跳歌 |
| 有副作用的请求 | 先确认幂等性、去重或服务端确认机制；失败后不能盲目重复喜欢、写入或创建任务 |
| 缓存 | 字节或条目上限、TTL/资源有效期、淘汰与失效时机、账号范围和释放责任；临时签名 URL 不永久入队列，不用无界 Map 积累封面或歌词 |
| 流式缓存与用户下载 | 按 03 分开管理；播放缓存淘汰不得误删用户下载；低空间与不完整资源有可见结果 |
| 分页 | 单页大小、并发请求和内存保留策略有上限；明确 cursor/offset、去重顺序和真实 `hasMore`，禁止一次拉全歌单来冒充分页 |
| 查询刷新与切账号 | 取消旧任务并更新代次；旧响应不能追加到新列表。追加失败保留已有内容，展示重试入口，不把失败当成末页 |
| 可见性 | 离开页面停止非必要轮询、歌词滚动和 UI 高频计时；后台仅保留播放或已获授权任务所需工作，避免重复收集和常驻唤醒 |

建议在调用点或对应配置旁写清预算依据，并将可调值集中在实际所有者边界。预算尚未确定时，记录待决事项和责任，不能借此提交无界实现。

### 8.1 首个公开版本的本地播放器

以下均为硬规则，适用于用户授权的本地音频导入、音乐库、检索、队列和播放；本地与在线仍共用第 5 节的单一播放服务，不新增第二个播放器。

- **扫描有界且可取消：** 本地扫描有明确任务所有者和用户取消入口；限制扫描范围、并发、每批处理量、单文件元数据/封面读取量及工作时间，达到边界时保存进度或报告未完成，不能宣称全量扫描成功。逐批响应取消，关闭 Cursor、流和元数据读取资源；重复扫描按范围与代次去重，旧扫描不得覆盖新结果。
- **URI 权限按范围管理：** 仅访问用户授权的音频或目录，播放只申请必要的读能力；记录 URI、实际授权范围和持久化状态。只有系统/提供者确实授予可持久化权限时，才按返回的授权能力调用 `takePersistableUriPermission`；保存 URI 字符串不等于保存权限。撤销、文件移动/删除、介质不可用时标记资源不可访问并提供重新授权入口，不擅自扩大为整个共享存储访问。[A5]
- **数据库增量维护：** 以稳定本地标识分批事务写入/更新索引，记录扫描代次与完成状态；列表、搜索、排序和分页从数据库按需查询。禁止把完整音乐库序列化成一大段 JSON，再在每次列表查询或刷新时全量读入、解析和排序。索引更新不能每次重建整个库，也不能在内存堆积所有音频与封面。
- **独立于在线账号：** 用户本地库与账号范围内的在线缓存/下载分别建模。本地浏览和播放不能以登录或网络成功为前提；退出、登录失效和切账号不得连带清空本地索引、撤销本地 URI 授权或中断无需账号权限的本地播放。账号资源仍遵守自身隔离规则，不能据此混用两类权限。
- **UI 不做 I/O：** UI 仅发送扫描/导入意图并展示进度；目录枚举、元数据读取、音频文件打开、索引读写由相应数据边界执行，保证 main-safe。播放命令回到播放器拥有的 Looper；不能以“本地很快”为由在 Composable 或主线程执行文件操作。[A4]
- **失败不清库：** 取消、扫描中断、单文件损坏、授权失败或数据库写入失败不能伪装成空库并删除已有记录。保留已成功提交的数据及原有库，明确部分结果和失败原因。只有对应授权范围完成可信扫描后，才能按定义的策略标记确实缺失的条目；用户明确移除范围时再处理其索引，不能把移除索引等同于删除原音频。

## 9. 错误语义与安全日志

硬规则：沿用 03 的领域错误模型，把网络、鉴权、资源不可用等原因在边界转换为可处理结果。不能将异常转换成 `emptyList()`、空字符串、`null` 或默认成功来掩盖失败。只有契约定义的“确实没有内容”才显示空态；离线旧缓存可以展示，但必须标明其来源或更新失败状态。

用户反馈说明发生了什么和可做的下一步，不直接展示原始响应或请求地址。取消通常结束旧操作，不产生误导性的错误提示；程序不变量被破坏应能诊断，不能捕获 `Throwable` 后悄悄继续。

硬规则：日志、异常消息、截图和测试样本不得包含 Cookie、token、密钥、密码、完整签名 URL、认证 header 或未经脱敏的账号响应。记录稳定错误码、阶段、耗时单位和必要的脱敏关联信息；日志级别、频率和容量有上限，禁止按每帧或每次进度回调无节制打印。保留诊断线索不等于输出原始秘密。

## 10. 注释与 KDoc

### 10.1 注释回答什么

新写解释性注释默认中文，标识符用英文；上游材料按第2节保留，`MediaSessionService`、`CancellationException`、`Retry-After` 等官方名称不翻译。修改行为时同步更新相关注释，不保留与实现冲突的历史说明。

注释应补足代码和类型不能直接说明的约束，按实际需要覆盖：

- **理由与不变量：** 为什么要保留当前策略，哪些状态组合不能出现，变更会影响什么。
- **线程与所有权：** 谁可读写，在哪个 Looper/dispatcher 执行，检查与提交是否必须连续完成。
- **单位与范围：** 毫秒/秒、字节、零基索引、包含或不包含的边界，特殊值及溢出约束。
- **取消与失败：** 谁能取消，取消后允许留下什么，哪些错误可重试，哪些返回值不代表成功。
- **资源处置：** 谁创建、移交和释放，失败/取消时如何收尾，释放是否需要指定线程。
- **协议限制：** 第三方接口的已知差异、依据的固定上游来源、兼容条件和不可假定的语义。

建议先用更准确的名称、局部变量或职责拆分消除理解障碍，再注释仍无法从代码得知的原因。注释长度以契约讲清楚为准，**不设任意注释百分比或每函数注释配额**。

### 10.2 KDoc 的范围和短例

硬规则：重要公共 API、跨模块复用逻辑及带有线程、单位、取消、错误或资源所有权约束的契约，必须提供 KDoc。简单 getter、明显的私有辅助函数和无额外约束的数据字段，不要求逐个补模板。首段说明用途，随后写必要契约；可用 `[parameter]` 关联参数，确有需要再写 `@param`、`@return`、`@throws`，不重复函数签名。[K1][K2]

以下为**纯 Kotlin 文档示例，未加入源码、未编译、不代表歌词实现**。它只展示索引、单位、前提和错误如何写清楚：

```kotlin
/**
 * 读取 [lineIndex] 对应的歌词开始时间，返回值单位为毫秒。
 *
 * [lineIndex] 从 0 开始，必须在 [startTimesMs] 的索引范围内；空列表没有合法索引。
 * 所选时间必须非负，列表在调用期间不得被并发修改；不检查其他行的时间或排序。
 *
 * @throws IllegalArgumentException 索引越界或所选时间为负数。
 */
fun lyricStartTimeMs(startTimesMs: List<Long>, lineIndex: Int): Long {
    require(lineIndex in startTimesMs.indices) { "歌词行索引越界" }
    val startTimeMs = startTimesMs[lineIndex]
    require(startTimeMs >= 0L) { "歌词时间不能为负数" }
    return startTimeMs
}
```

这个函数没有 IO、挂起或资源所有权，因此无需塞入无关的线程和取消模板。真实解析器若有排序、偏移或取消要求，应在它自己的契约中说明，不能从此例推定。

### 10.3 行内注释解释原因

以下同样是文档示例，代次比较只演示注释写法；真实状态提交仍须在拥有者上下文内连续完成校验与写入：

```kotlin
private fun acceptsResponse(responseGeneration: Long, activeGeneration: Long): Boolean {
    // 取消请求后旧回调仍可能抵达；拒绝旧代次，避免它覆盖用户刚切换的查询结果。
    return responseGeneration == activeGeneration
}
```

硬规则：禁止逐行复述代码，例如在自增前写“加一”、在请求前写“发送请求”；禁止大段注释掉的死代码、无效模板和装饰性分隔墙。历史方案放在有依据的决策记录中，不在源码保留第二份失效实现。

禁止新增文件作者署名、作者邮箱、`@author` 模板或 AI 署名。依法必须保留的上游许可/版权材料按 [11-上游复用实施指南](11-上游复用实施指南.md) 处理，不能当作个人文件头模板；如材料包含受仓库政策限制的个人信息，先解决合规保留方式，不能擅删许可或直接泄露信息。

TODO/FIXME须关联真实任务及可验证退出条件；已有DEV/CI编号或真实Issue均可，责任人可在任务记录中维护，不要求每条另开Issue或重复写owner。例：`TODO(DEV-216): 完成URI失效恢复；T-39通过后移除`，仅示范格式，不代表源码已有该待办。无依据的“以后优化”、虚构编号和用TODO放行当前阻断问题均不可接受。

### 10.4 例外与检查抑制

硬规则：`@Suppress`、lint 抑制、工具排除或规范例外必须写明规则名、具体原因、最小适用范围、关联记录和验证方法；临时例外还要有责任人及移除条件。优先只作用到必要声明，禁止用文件级、目录级或全局关闭来掩盖局部问题。

审查必须核对误报/兼容条件确实存在，运行相关验证，并确认抑制未覆盖新的真实问题。例外说明不是自行豁免权限；真实的线程违规、吞取消、秘密泄漏和治理限制不能用 suppression 消除。偏离120列软参考不需要申请豁免；函数/文件长度按职责审查，没有行数门禁。

## 11. 可读、可测量的性能优化

硬规则：优先修复用户可感知的阻塞、重复请求、无界分配、后台无用工作和播放竞争。优化前说清具体场景与瓶颈，优化后保留能复查的证据；没有测量时只能称为待验证假设，不能宣称“更快”“更省电”。性能预算、P0冻结标准和诊断/发行产物区分统一按14执行。

性能变更记录至少包含：用户场景与数据规模、基线和候选source/build SHA、云端产物及诊断/发行差异、设备/固件、测量方法与次数、适用指标、波动和功能回归；同条件同类型产物比较，各设备单独结论。纯可读性重构可以说明行为未变，不必伪造性能数字。

建议先采用能顺序阅读的算法和有界数据结构。只有证据表明实际热点受益时，才引入特殊缓存、对象复用、索引或算法复杂度；同时说明失效条件、空间成本和回退方式。不能为了减少几行或猜测分配成本写难以维护的技巧，也不能用注释替代必要的结构改善。

硬规则：优化后保留队列、错误、取消和恢复语义；视觉动画、封面处理与歌词刷新按可见性和预算降级。不能通过延迟关键控制反馈、隐藏错误或破坏圆屏操作换取漂亮指标。
