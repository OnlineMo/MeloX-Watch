## 1. 固定环境与最小接入

`.ci/toolchain.properties` 是主要工具版本的唯一依据：Ubuntu 24.04、Temurin 17.0.17+10、Gradle 8.13及发行包SHA-256、AGP 8.11.1、Kotlin/Compose编译插件2.2.21、compile/target SDK36、minSdk候选26、Build Tools35.0.0、command-line tools13114758。不是“最新版”，本轮不升级。

Android 官方 AGP8.11 兼容表及 Kotlin 兼容表是选型依据；具体 Compose UI、Media3、Room、网络和图片依赖在 DEV-004-A 中记录精确版本、传递依赖与校验，云端成功后冻结。不能把“工具链安装成功”当作这些依赖已经兼容。runner预装工具和SDK修订可能变化，产物记录实际版本，不承诺重新构建字节相同。

Android依赖只随实际功能引入：DEV-004-A先锁探针必需组件，Room/图片等在首次使用前锁定并验证，而非为探针安装全部未来依赖。格式/静态分析工具也先选一套能匹配锁定Kotlin版本的最小组合，在CI-01接入时验证，不要求为每个文档PR启动全套性能工具。

DEV-001 可先采集设备只读信息。DEV-004-A 从现有 `Bootstrap cloud toolchain` 下载 wrapper（过期则在云端重跑），在本地编写最小 app，在云端构建探针，供DEV-002/003/005验证。DEV-004-B 再记录基线；P1扩充同一工程，不重复新建探针仓库。首期一个 `:app` 模块内分职责包，详见03。

工程根为 `android/`，flavor为`watchAndroid`。计划包名 `io.github.onlinemo.meloxwatch`，Debug为该名加`.dev`；候选/正式包名与正式证书一致。CI脚本已校验**精确包名**、版本和证书，但尚无真实APK验证。minSdk/ABI由探针核验后冻结；与设备不匹配时先改计划/锁文件，不偷偷本地换环境。

Gradle任务为 `:app:testWatchAndroidDebugUnitTest`、`:app:lintWatchAndroidDebug`、`:app:assembleWatchAndroidDebug`；候选使用对应Release任务。应用脚本从根仓库的工具链和version文件读取配置，不让flavor或输出重写版本。`settings.gradle.kts`加入环境检查，阻止本地Gradle执行；该检查是工作约定，不是对恶意构建脚本的安全隔离。

## 3. 信任与签名分离（CI-01目标）

1. **PR编译**：执行PR/合并树的应用代码，token只读、不传签名秘密、不持久化checkout凭据、缓存只读；使用临时Debug证书。普通`pull_request`事件名不是绝对无秘密保证，特别是同仓库PR；必须由实际job权限和secret传递路径保证。
2. **可信分支编译**：编译/测试/lint也不接收稳定Debug或Release密钥，不持有contents写权限。需要签名的APK先作为未签名产物输出，记录精确SHA、构建模式和校验。
3. **签名job**：新runner，仅运行已审阅的签名/验证工具，从同一受信任run按固定artifact ID取包；不运行Gradle、PR脚本或产物中的程序，不恢复不可信可执行缓存。核验仓库、事件、ref、源SHA、构建成功后再用对应证书签名；发布前再次核验包名/版本/证书/哈希。
4. **发布job**：不需要签名密钥、不执行Gradle，只验证同一候选与验收记录、创建新tag并上传已有APK；仅该job需要短期`GITHUB_TOKEN`写权限。没有PAT/deploy key或新的长期仓库写凭据。

证书指纹固定在`.ci/signing-certificates.json`。密钥只在必要job的必要步骤可见；环境隔离/审批可在套餐支持时增强，不能把未启用的environment保护当事实。受信任代码审查依然必要，不能将产物哈希当成“代码无害”的证明。

## 4. 候选、测量与公开产物

已部署同一`Owner release`网页入口的两个明确操作（CI-02/03）；目前只有政策接线与无工程拒绝证据，**没有实际候选或发布**：

| 操作 | 输入与前置 | 输出与副作用 |
| --- | --- | --- |
| prepare-candidate | OnlineMo在main填写versionName/prerelease；基础编译检查与签名条件满足；不要求最终设备报告、公开或owner_approved | 冻结当时main source SHA、版本计数与仅改版本文件的detached快照；云端测试/lint/优化Release编译及隔离正式签名；输出候选APK、manifest、校验和快照Git对象包；**不推分支/tag、不创建Release、不公开** |
| publish-candidate | OnlineMo明确授权，填已验run ID/attempt/artifact ID；12全部证据与保护通过 | 下载并验证同一APK和快照，**不重新编译、改版本或重签**；用短期token推新tag、创建/恢复对应Release |

构建与签名产物须带候选记录：versionName/code、source SHA、snapshot/build SHA、完整main可达提交数、历史最高code、实际APK/证书SHA-256、run/attempt/artifact ID、工具链及锁文件摘要。快照Git对象用受校验的bundle等数据保存，发布时可还原**同一commit**，不靠重做一次commit获得相似内容。产物本身不包含签名私钥。

正式候选默认非debuggable、非profileable。需要自动化trace或基准测试时，云端另生成相同代码/优化条件的诊断包及测试APK，用不同标识注明差异；诊断数据只支持定位，最终可在发行包测得的启动/交互/音频/后台指标仍在发行APK复核。设备不支持某工具时按14预先冻结的替代测量执行，不临时拿Debug数据充数。

候选与验收报告提交之间的关系、code冻结、恢复规则以 [10发布流程](10-仓库治理与发布.md) 为准。报告可以在候选之后提交，但不能因此重建已验APK。

## 5. 每次开发与本地验证

本地只编辑、Git、文本/政策检查、文件校验以及设备安装/测试/采集。Gradle sync/编译/单测/lint、Kotlin/Java编译、Android Studio Build/Run全部走GitHub Actions；不通过伪造CI环境变量本地补编。诊断APK、instrumentation测试APK也必须云端构建。

1. 从contribution建立主题分支，完成适当局部检查并提交；PR触发云端构建。当前手动调度任意主题分支可能跳过Android job，不得误以为获得APK；应用阶段主题改动以PR云端结果为准，或在CI-02中明确支持owner选定ref且无秘密的测试构建。
2. 下载对应APK/manifest/SHA256SUMS，核对source与实际build SHA（PR可能为merge SHA）及签名。PR临时证书与稳定`.dev`可能不能覆盖，不能自动卸载掩盖；需要覆盖回归时使用经审阅的稳定分支包。
3. `adb install -r`只安装已校验云端包，填写设备/性能/视觉记录，失败本地改代码再云端重建。不运行未获设备授权的清数据、卸载或修改系统设置。
4. 低影响文档改动只核对文本/链接，云端现有门禁照常运行；不新增模拟应用测试来凑通过记录。

## 6. 产物留存与失败恢复

当前配置为Debug artifact14天、报告7天；快照、优化未签名/签名产物、候选及locator为90天，Release编译报告30天。实际APK留存/恢复仍待验证；到期前保存完整受校验候选包到所有者控制的位置。源码重新构建的包不能自动替代已验包，候选过期/损坏且无可校验原字节时重新准备并重新验收，不在已有tag下重建。

tag前失败没有发布点；tag后上传中断按10幂等恢复。不得删除tag、覆盖已有不同哈希资产或在同版本下偷偷重编译。整个流程不回写main/contribution，所有分支仍是开发/文档分支，没有额外发布分支。

官方依据：`https://developer.android.com/build/releases/past-releases/agp-8-11-0-release-notes`、`https://kotlinlang.org/docs/gradle-configure-project.html`、`https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions`。平台与工具行为在实现CI任务时再按当时版本核对，不能将历史网页当运行证据。


## 7. 全量本地需求增加的云端产物契约

LP-14交付真实Android手机配套应用，不能只给网页或手表里的占位入口。工程起步仍只有`:app`；进入LP-14时在同一`android/`下增加`:companion`，计划包名`io.github.onlinemo.meloxwatch.companion`，Debug追加`.dev`。按03固定正式名称，首次发行前同步精确包名校验。两端共用工具链和根`version.properties`，不另立可由贡献者修改的版本来源。

手机端编译、单测、lint、测试APK同样全部走云端；本地只编写、下载校验与真机验证。LP-05引入原生解码依赖时，先在同一锁定环境固定其版本/源码摘要、NDK/CMake（如需要）、ABI、许可和构建步骤，再用云端验证；不得临时在本机编译解码库。

LP-14须同步扩充云端构建/签名/候选manifest与逐包验证，不能直接复用只处理手表单APK的脚本后宣称交付完成。具体workflow仍先提交Actions Issue，由所有者维护；当前CI前置源码尚未实现手机APK处理，本节的配套产物契约需在LP-14独立落实。

候选是同一冻结快照的一组必需产物：手表APK＋手机APK；诊断/测试APK另行标识。manifest逐项记录角色、精确包名、版本、ABI、SHA-256、证书指纹、构建任务、run/attempt/artifact。可信Debug和正式包各用已有对应证书，两端不同包名，不复用上游签名；若未来决定独立手机证书，需另行更新签名契约，不能静默换证。

验收同时绑定两端包和协议schema版本，覆盖配对/断连/修订冲突/取消/恢复以及独立播放。发布上传验收过的整组原包，不在发布时补编手机包；任一必需产物变更，都重新准备候选并回归受影响项。现有单APK云端成果不证明多APK契约已实现。
