首次依赖资料只允许在无秘密的Debug PR中采集：缺少已提交的`android/gradle/verification-metadata.xml`或`android/app/gradle.lockfile`时，云端使用`--write-verification-metadata sha256 --write-locks`解析三种变体的编译/单测/lint依赖，将结果保存到既有reports上传路径，并明确失败，禁止导出APK或进入稳定签名。资料按source/build SHA审阅后提交；成功构建只用严格校验和锁定输入，不自动生成。可信分支和候选缺资料直接拒绝。生成资料不是应用验收或可信产物。

当Room当前schema尚无已提交的云端原导出时，同样只允许无秘密Debug PR采集；旧schema和已审依赖输入不删除。仅缺当前schema时采用独立的schema-only合同：依赖XML、app lock、已有可选root lock与全部旧schema须为普通仓库内文件、没有符号链接，并与HEAD原blob字节一致；当前schema须实际不存在，不能消费未提交的旧失败导出。manifest schema_version=3、collection_kind=`room-schema-strict-variants`，按strict-debug、strict-release、strict-diagnostic三个独立Gradle调用，各执行完整test/lint/assemble，保留存在时的Diagnostic AndroidTest编译。全程严格锁/hash，不加writer flags、不调全配置collector；新配置/制品缺锁/hash直接失败，不回落到writer或导入失败材料。

schema-only开始固定reviewed_input_hashes；每次调用前后核验全部依赖和旧schema集合/字节不变，当前schema是唯一允许新增项。每变体成功后保存本次新schema原件到schema-exports/<phase>/<version>.json，再仅删除本run刚生成、尚未审阅的current文件，让下一变体独立导出；绝不删除已提交旧schema。三个导出必须同字节，缺导出、额外新schema/root lock、任意输入漂移或报告复制漂移都失败。manifest的current_schema、reviewed_input_hashes、schema_exports与strict_input_hashes明确绑定资格；本地reader必须按新合同审核，旧schema2 reader不能默认为接受。该路径仍generated-unreviewed、accepted=false、apk_exported=false，独审原字节提交后还须普通严格构建。它减少静态调用请求，实际耗时和原生崩溃修复仍待精确云验。

schema-only在创建报告目录、执行下一变体、写入每份导出/复制件与最终manifest前检查固定目的地及父目录没有符号链接；每次严格边界检查完整输入集合的文件与父目录，不只比较哈希。目的地初始不安全时零Gradle调用、零报告写入；旧输入目录在首变体后漂移时立即停止，不继续后两种变体。报告保存失败不能替换已经观察到的原CalledProcessError或BuildTimeout对象，只能添加固定、有界的报告不可用note；无法安全保存的报告明确未获证，不保证存在failed-partial文件。reader同时检查manifest与独立冻结binding的SHA字符串格式、run/attempt为正整数且不是bool，以及schema_version为整数3；保存的JSON与传入原件须连数值类型一起相同，不能以True==1或3.0==3通过。

完整路径的三个writer只有全部完成才能进入normal；normal完成后固定完整依赖和全部schema字节，三个STRICT调用逐次核验相同输入。两种路径任一步失败、无输出/测试/阶段/总超时或输入/report漂移，都停止后续；报告可安全保存时保留failed-partial，报告本身不可用也不能推断成功。报告必须等于最后的严格输入，要求的全部阶段及schema-only三个独立导出不得缺失。收齐不代表accepted：仅完整generated-unreviewed原件可进入独立官方hash、锁、schema/迁移和报告审阅；原字节审阅提交后还须普通严格构建，bootstrap从不导出或签名APK。不能删除旧pins强制采集或自动回落掩盖失败。

普通构建与v2/v3/v4全过程共享2700秒总期限，只有上述完整校验的显式v5六阶段使用5400秒；每次调用1200秒、无输出300秒、单测试完整生命周期240秒、heartbeat30秒不变。分拆不重置总期限、放宽原测试期限或跳过变体。监控继续绑定source/build SHA与run/attempt、保存步骤UTC和耗时，准备超过300秒、编译步骤超过600秒告警并每300秒提醒；必须记录实际通知与交接延迟。步骤状态和线程单点不能代替内部进度，失败产物不因Debug单测通过而合格。

Test JVM关闭core dump，并将原始hs_err写在`app/build/ci-native-crash/<phase>`，位于自动reports上传范围外。自然失败或超时完成原有进程回收后，wrapper才从三个固定非递归目录尝试采集本次新错误文件；旧名字、目录/文件身份漂移、链接、过限或不完整基线均不获诊断资格。最多尝试读取4个文件、单件2MiB、总读取预约4MiB，共用2秒采集循环期限；原始错误文件不复制进reports。自动摘要只允许固定fatal分类、白名单模块相对偏移、代码class/member标识及经过校验的phase/source/build/run/attempt和哈希，没有环境、命令行、地址、线程名、URL或私人路径。采集缺失与保存失败保持原CalledProcessError/BuildTimeout及清理优先级，不代表SIGBUS根因已确定；Linux实际路径、JVM flags、Gradle接线和额外耗时须由新云端原件验证。

## 3. 信任与签名分离（CI-01目标）

1. **PR编译**：执行PR/合并树的应用代码，token只读、不传签名秘密、不持久化checkout凭据、缓存只读；使用临时Debug证书。普通`pull_request`事件名不是绝对无秘密保证，特别是同仓库PR；必须由实际job权限和secret传递路径保证。
2. **可信分支编译**：编译/测试/lint也不接收稳定Debug或Release密钥，不持有contents写权限。需要签名的APK先作为未签名产物输出，记录精确SHA、构建模式和校验。
3. **签名job**：新runner，仅运行已审阅的签名/验证工具，从同一受信任run按固定artifact ID取包；不运行Gradle、PR脚本或产物中的程序，不恢复不可信可执行缓存。核验仓库、事件、ref、源SHA、构建成功后再用对应证书签名；发布前再次核验包名/版本/证书/哈希。
4. **发布job**：不需要签名密钥、不执行Gradle，只验证同一候选与验收记录、创建新tag并上传已有APK；仅该job需要短期`GITHUB_TOKEN`写权限。没有PAT/deploy key或新的长期仓库写凭据。

证书指纹固定在`.ci/signing-certificates.json`。密钥只在必要job的必要步骤可见；环境隔离/审批可在套餐支持时增强，不能把未启用的environment保护当事实。受信任代码审查依然必要，不能将产物哈希当成“代码无害”的证明。

## 5. 每次开发与本地验证

本地只编辑、Git、文本/政策检查、文件校验以及设备安装/测试/采集。Gradle sync/编译/单测/lint、Kotlin/Java编译、Android Studio Build/Run全部走GitHub Actions；不通过伪造CI环境变量本地补编。诊断APK、instrumentation测试APK也必须云端构建。

1. 从contribution建立主题分支，完成适当局部检查并提交；PR触发云端构建。当前手动调度任意主题分支可能跳过Android job，不得误以为获得APK；应用阶段主题改动以PR云端结果为准，或在CI-02中明确支持owner选定ref且无秘密的测试构建。
2. 下载对应APK/manifest/SHA256SUMS，核对source与实际build SHA（PR可能为merge SHA）及签名。PR临时证书与稳定`.dev`可能不能覆盖，不能自动卸载掩盖；需要覆盖回归时使用经审阅的稳定分支包。
3. `adb install -r`只安装已校验云端包，填写设备/性能/视觉记录，失败本地改代码再云端重建。不运行未获设备授权的清数据、卸载或修改系统设置。
4. 低影响文档改动只核对文本/链接，云端现有门禁照常运行；不新增模拟应用测试来凑通过记录。

## 8. 双APK后继与500分钟月度构建约束

根据2026-11-21的日常构建预算约束，采用两端各一次完整Debug测试，避免重复三变体完整套件。500分钟/月是当时私有阶段的规划约束；开发公开后的运行仍按实际阶段与期限监督。本文第1节的v2/v3/v4/v5、request整数1/2、manifest整数2–5及旧六阶段资料是历史合同；原件、旧pin与各版本reader仍保留。进入LP-14后的新执行由本节独立后继控制，不能把CI31的V3导出改写为当前V7资料，也不能将新schema字段套到旧报告。后继实际云耗时、双包产物、设备和互操作验收均未因此通过。

| 场景 | 可见步骤与真实任务范围 | 应用阶段总期限 |
| --- | --- | --- |
| 普通有效源码改动 | start → test-debug → lint-build → seal；手表与手机各一次完整Debug单测，随后两端Debug lint/assemble | 1200秒 |
| 显式依赖/当前schema改变 | start → acquire → strict-inputs → seal；一次真实编译/lint/Test.classpath归档采集，再严格编译/lint校验及独立当前Room导出；不执行应用Test或APK assembly，最后报告型拒绝 | 1800秒 |
| 正式候选准备 | 同一snapshot在一个compile-candidate runner内执行一次两端完整Debug套件，然后Release/Diagnostic lint/优化APK及存在时的AndroidTest编译；分开上传两个unsigned artifact，交给各自新签名runner | 1800秒 |
| 仅文档、报告、readiness或workflow/action | 政策/文本检查；android-compile及签名明确skipped，cloud-gate不得称其为APK通过 | 无Android调用 |

三个应用期限从start起使用同一runner的monotonic原点，跨命名步骤通过session SHA-256链绑定；步骤不可重复、跳过或重排，不可改预算或重置时钟。工作流另以job timeout限制安装/恢复及收尾：普通preflight10分钟、compile35分钟、独立Debug签名10分钟、gate2分钟。这里给的是硬拒绝边界，未宣称实际耗时或节省比例。原每进程1200秒、无输出300秒、单测试完整生命周期240秒、heartbeat30秒与失败进程回收继续有效。普通/候选的完整Debug Test禁用该任务的up-to-date和测试结果cache，以取得本run的真实JUnit；编译缓存继续使用。lint-build、acquire和strict-inputs的task graph拒绝业务Test任务；两项采集阶段另拒绝APK package/assemble任务。发生具体Release/Diagnostic问题时，先记录问题及需验证的范围，再安排专项验证；日常不隐式重复三个完整套件。
