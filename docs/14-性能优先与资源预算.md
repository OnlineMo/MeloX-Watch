# 性能优先与资源预算

状态：强制开发与验收规范，2026-11-10 建立。应用尚未实现，以下数字是项目预算，**不是实测成绩或设备性能保证**。本文件是性能阈值的唯一来源；06 文档维护测试场景，15 文档维护视觉标准，16 文档维护代码规范。

## 1. 决策顺序

**性能第一，界面美观第二，可读性必须达标。** 正确性、数据安全、隐私、基础可访问性是不可交换的前提，不允许通过错误播放、删除数据、缩小点击区域或隐藏失败来“优化”。

性能具体包括持续播放可靠性、交互响应、启动、内存、CPU/GPU、耗电和安装体积。先保证播放与输入，再安排非关键工作。卡顿、发热、持续耗电或无界内存不能用“界面更炫”作为接受理由；性能达标后，页面仍必须通过 [视觉验收](15-界面设计与视觉验收.md)，不能交付临时拼凑的 UI。

每个功能按“明确数据与资源边界 → 最小完整实现 → 云端构建 → 同条件实测 → 调整 → 视觉验收”推进。优化要有瓶颈和前后证据，不靠层层抽象、提前缓存所有内容或难以理解的技巧。优化代码同样执行 [可读性规则](16-代码规范与可读性.md)。

## 2. 不可违反的资源约束

| 编号 | 约束 | 审查与验证 |
| --- | --- | --- |
| PERF-01 | 一个播放服务、一个活动播放器；在线、本地文件和未来下载共用播放内核 | 反复进出页面、切换来源后核对实例/会话与声音；不得通过隐藏第二个播放器预热 |
| PERF-02 | 主线程不进行网络、磁盘、数据库查询、目录扫描、封面解码或大批解析/排序 | 调用链审查；开发诊断和 trace 定位。Media3 操作遵守其所属线程，不把播放器调用随意搬到 IO 线程 |
| PERF-03 | 列表真实分页，逐批查询；首屏不等待整个音乐库 | 1000 首及空库样本；不能先读全库再 drop/take 假装分页。小型固定菜单不强制使用复杂分页组件 |
| PERF-04 | 每种缓存有容量、淘汰、生命周期和清理边界 | 不用无界 Map 存曲目/图片/歌词；缓存在账号或来源切换时按所有权处理。外部本地文件不能当缓存删除 |
| PERF-05 | 页面不可见/熄屏时停止页面动画、滚动、进度采样和非必要轮询 | 活跃音频服务继续工作；播放器解码、必要缓冲和用户已启动的任务不能随页面一起误停。无任务时不保活 |
| PERF-06 | 任务可取消、请求可去重、重试有次数和退避上限 | 新搜索/新点歌不会被旧结果覆盖；权限失败不循环重试；取消不能转换为成功空列表 |
| PERF-07 | 封面按显示尺寸请求/解码，先占位后补图 | 不在滚动时读取全尺寸封面；缓存按像素/字节限制；切歌不等待封面和歌词 |
| PERF-08 | 本地扫描使用有界工作队列和增量索引，播放优先 | 扫描不为每个文件或目录创建一个独立并发任务；不能每次启动全盘扫描，不在首次扫描中解析全库歌词/封面 |
| PERF-09 | 进度变化不使整页、整库或队列模型高频重建 | 状态分区；列表稳定身份；测量后才引入 remember/derivedStateOf 等优化，不用稳定性注解掩盖可变对象 |
| PERF-10 | 不通过常亮、无限唤醒、周期后台扫描或盲目提高重试频率维持功能 | 核验资源持有者、释放条件及后台行为；系统限制明确记录，不伪造后台稳定性 |
| PERF-11 | 用户自定义解析服务默认零开销，按需调用且有总预算 | Meting 关闭/未配置/本地模式零请求；正常网易云解析成功不额外串行请求；异常补充解析有界、可取消，不预解析全歌单，见19 |

### 初始调度值

以下是项目起始配置，可在 P0/P1 通过证据调整并记录理由，不是平台推荐值。

- 播放页可见时进度摘要最多每秒刷新一次；可见歌词页初始最多每秒采样 5 次，仅当前行/所需位置变化时更新。拖动进度条直接响应手势，不等待定时采样。
- 本地扫描/元数据读取全局并发初始为 1；按小批提交索引，候选批量 100 项。SQLite/Room 写入事务不能包住文件系统遍历；取消时保留上一完整索引和已确认结果。
- 下一曲最多预取一份轻量元数据；首版不使用第二播放器、全歌单预缓冲或全曲复制做“秒开”。
- 同一请求键合并重复工作。封面、歌词先服务当前可见内容；扫描、未来下载或封面补全与播放争抢资源时降速/暂停非关键工作。
- 音频缓存与下载的容量沿用 [产品默认值](02-产品需求与范围.md)。封面/歌词缓存另列容量，不能共用“无限剩余空间”假设。具体容量须在 P1 记录，未给出上限不得合入实现。
- 二维码轮询遵守协议节奏与服务端限制；离开页面、过期、成功或用户取消后停止，不为统一帧率提高网络频率。

## 3. 首版性能预算

P0 建基线，P1 开始回归，P2（含本地阶段）/P3 达到首版门槛；P5 继续扩展验证，**不能把性能问题推迟到 P5 才处理**。预算变更需单独说明原因、设备证据与影响，得到所有者确认；不得在同一性能失败中静默放宽阈值。

| 指标 | 初始验收预算 | 测量与适用范围 |
| --- | --- | --- |
| 冷启动到可操作首页 | P95 ≤ 3 秒 | 优化候选包 30 次，记录 P50/P95/最差；不等待扫码、全库扫描或网络请求才允许操作 |
| 本地文件首声 | P95 ≤ 1 秒 | 20 次，固定格式/采样率样本；已连接蓝牙耳机；设备首连另报。首版本地库适用，P4 下载库复用此预算 |
| 在线已登录首声 | 健康 Wi-Fi 下 P95 ≤ 4 秒 | 20 首，记录资源解析/连接/缓冲分段；保留超时与失败数量，不从统计里静默删掉慢样本 |
| 主要操作反馈 | UI 可见反馈 ≤ 100ms；可执行的暂停/切换等音频动作 P95 ≤ 300ms | 缓冲期间不能把按钮视觉变化当成音频动作完成；本地和在线分别记录 |
| 稳态 PSS | 目标 ≤ 180 MiB | 完整应用进程集合；1000 首索引、分页列表和播放并行，封面缓存预热后采样 |
| 重复操作内存 | 100 次进出/切歌后相对预热基线增量目标 ≤ 20 MiB，且无持续上升趋势 | 记录全时序与有界缓存填充；不只挑结束点，不以人工强制 GC 后数值代替真实运行 |
| 帧耗时 | 主要列表/页面过渡中，超过两帧实际刷新周期预算的帧比例 < 5% | 同时记录总样本、P50/P95/P99、实际刷新率与原始 trace；不能用平均 FPS 掩盖卡顿 |
| 歌词偏差 | 固定本地样本目标 ≤ 250ms | 区分 LRC 文件自身偏移与实现偏移；seek/切歌/手动回到当前行均测 |
| 安装包 | 主 ABI 优化 APK 目标 ≤ 30 MiB | 排除歌曲；列出新增依赖和增量。未实测前不引入重型解码器/字体库只是为了多一个特效 |
| 在线熄屏 | 蓝牙耳机连续 60 分钟，无应用侧异常停播 | v0.1.0 门槛；外部网络中断单列并验证恢复，不伪造稳定网络 |
| 本地熄屏 | 无互联网、无账号依赖，蓝牙耳机连续 120 分钟，无应用侧异常停播 | v0.1.0 本地音乐门槛；P4 增加下载文件的同条件回归 |
| 耗电 | 相对同条件最小播放基线，额外耗电目标不超过 20% | 至少 3 轮、每轮 60 分钟；在线/本地、亮屏/熄屏分别测。基线接近零或电量粒度不足时延长采样，不能宣称达标 |
| 本地库并行扫描 | 扫描时仍满足交互/内存/连续播放预算 | 首扫、增量扫各用 1000 首，计时/CPU/温度可见；首扫总时长先建基线，不能用最快的几首推算全库 |

“无持续增长”需要至少对预热后第 20、50、100 次操作的区间观察并保留记录，不靠一次结束截图判断。更大音乐库（例如 5000 首）作为扩展压力测试；未测容量不作为对外支持承诺。

## 4. 可复核的测量方法

### 同一来源、同一条件

所有 Android 包和基准测试 APK 均在 GitHub Actions 构建；本地只安装、执行设备测试和采集分析。日常 Debug 可验证行为，但不能与启用优化的发布候选混用来证明性能改善。未来需要不发布的优化/profileable 候选与测试产物时，先按 Actions Issue 流程接入；当前仅有规划检查、Debug/Release 配置，不宣称已有性能测量 workflow。

记录 source/build SHA、run/attempt、APK SHA-256、构建类型/是否优化/调试或 profileable、依赖与固件。使用同一 Watch X2、音量、耳机、网络、亮度、电量模式和接近的温度；基线与候选交替测量，明显热降频或充电的结果单列。首次初始化、冷启动、热启动、缓存命中与未命中不能混成一个数字。

### 指标不能混算

- 启动的“可操作”必须定义页面和按钮可用终点；只出现启动画面或首帧不算。冷启动是进程冷启动，磁盘/系统缓存条件仍需注明。
- 首声是实际输出音频的终点；播放器进入 READY、发出播放命令或进度开始变化只能作为分段指标。若只采集到内部事件，应明确写“代理指标，首声未验收”。
- P95 采用排序后 nearest-rank：索引 `ceil(0.95 × n)`（从 1 起）。20 次和 30 次是初始有限样本，需要同时报告原始值和失败数，不据此声称总体绝对保证。
- 帧周期取 `1000 / 实测刷新率Hz`；以平台帧时间线区间/完成期限记录计算预算。刷新率变化须分段。`frameDurationCpuMs` 只代表 CPU 工作，`frameOverrunMs` 是超过期限的时间，两者都不能直接冒充完整帧端到端耗时。若使用 overrun 指标，独立报告名称与分位数，不与“两帧耗时比例”混算。
- 可用工具依设备 API 而异；例如 Macrobenchmark 的 `frameOverrunMs` 指标要求 API 31+。无法采集指定指标时，使用兼容的帧统计/系统 trace 并解释口径，或记未测；不能填 0。模拟器不是 Watch X2 性能验收证据。
- PSS 记录 MiB、进程集合和采样时刻；Java heap、native heap 与 PSS 不互相替代。CPU、GPU、温度和扫描时间先记录同条件趋势，不凭空承诺一个通用百分比。
- 耗电同时报告每小时绝对下降百分点和对基线的相对变化；基线与候选使用相同音质/格式。整数电量的测量精度不足时应延长观察，不能把两个“下降 1%”解释为精确相等。

### 回归判定

超过已冻结预算或出现播放中断、ANR、无界增长，先停止扩展功能并修复。即使仍在绝对预算内，关键耗时/PSS/耗电相对同条件基线恶化超过 10% 时进入复核：再做两组相同条件的对照，报告波动和绝对差异。确认回归后须优化或回退，不用新基线覆盖旧结果；显著但必要的取舍须由所有者明确决定，不能由 agent 静默豁免。

重复失败、撤销权限和取消扫描必须包含在性能验证中；只有成功路径很快并不足以通过。填写 [性能验收记录](templates/性能验收记录.md)，保留脱敏 trace、样本、截图及结论。

## 5. 每阶段完成定义

| 阶段 | 必需性能交付 |
| --- | --- |
| P0 | 设备/显示参数、最小单播放器基线、真实本地文件可达性与格式探针；标明初始预算未测项 |
| P1 | 单播放器、线程/资源归属、主页启动与控制基线；缓存上限；最小视觉组件；不依赖线上接口测试基本音频 |
| P2 与 P2-L | 在线分页及本地增量索引，取消/错误恢复；1000 首库与扫描并行播放；记录单个模块是否导致内存/响应回归 |
| P3 / 首版 | 14 的首版预算、15 的视觉矩阵、16 的可读性审查，在线 60 分钟与本地 120 分钟熄屏全部有证据 |
| P4–P5 | 扩展下载与存储压力、升级/异常恢复；维持已有在线/本地基线，不能因新功能降低旧功能质量 |

文档 PR 可以标性能实测“不适用”，但涉及 UI、数据库、播放器、扫描、图片、依赖或生命周期的实现 PR 必须说明受影响指标和证据。未接设备时允许继续独立工作，受影响的验收项保持未测，不宣称可发布。
