# 性能优先与资源预算

终审：2026-11-11。应用尚未实现。范围以 [21 全量整合](21-本地播放器全量需求整合.md) 及其 [128项/256AC矩阵](requirements/local-player-coverage.json) 为准，全部必做；本文是性能预算和测量口径的唯一依据；**初始数字不是实测结果，也不是设备性能保证**。测试场景、视觉与代码规则分别见 [06](06-测试验收与风险.md)、[15](15-界面设计与视觉验收.md)、[16](16-代码规范与可读性.md)。

## 1. 决策顺序与冻结点

**性能第一，界面美观第二，可读性必须达标。** 正确性、隐私、数据完整性和基础可访问性不可交换。先保证持续播放、控制和输入，再安排扫描、图片及装饰；不能靠错误播放、隐藏失败或缩小触控目标改善数字。

本文区分三类要求：资源/正确性硬约束始终生效；表中数值是可执行的初始目标；P0以当前主测Watch X2探针冻结该设备的条件、方法和验收标准；产品面向普通Android智能手表，不限定型号。尚未具备完整场景的指标保留初始目标进入 P1/P2 验证，不能因为“待测”删除上限或填写通过。冻结记录注明适用场景、样本、容差和依据。

预算调整必须有设备证据、理由、影响及所有者决定；未调整前继续使用原值，**稳态 PSS 初始目标仍是 180 MiB**。P0据探针选择并冻结缓存/调度配置，P1按冻结值实施；后续变更仍需上述证据和所有者决定，记录新旧值及总资源影响，不能在失败后临时降低验收线。性能从 P0/P1 建立并持续回归，不推迟到 P5。

其他设备按API/ABI、窗口/形状、音频、后台、输入与文件授权能力建矩阵，不用型号白名单。其性能与耗电须建立独立实机基线并冻结适用预算；可沿用初始目标作起点，不能直接继承Watch X2实测结论或任意放宽硬约束。Wear OS专项整合另按后续阶段执行。

### 初始配置

以下是项目工程起点，单位 MiB 为 1024² 字节；容量达到上限必须淘汰、停止或给出明确状态。

| 项目 | 初始值及范围 |
| --- | --- |
| 封面内存缓存 | 8 MiB，按解码后字节计量、LRU；当前显示及临时解码占用仍计入进程 PSS |
| 封面磁盘缓存 | 32 MiB，按实际文件字节计量、LRU；不可清理用户原封面/音频 |
| 歌词缓存 | 内存上限 8 MiB，计入原文和解析对象；若持久缓存歌词，磁盘也单独限 8 MiB；用户授权的 LRC 不属于可淘汰缓存 |
| 单份 LRC | 原始文本最多 1 MiB、10000 行；展开后的时间线条目也最多 10000，流式检查边界；超限显示歌词不可用，音频继续 |
| 扫描/元数据读取 | 全局并发 1、候选批量 100 项；事务不包目录遍历，批次可取消，失败保留原库及已确认结果 |
| UI 采样 | 可见播放页进度最多每秒1次；逐行歌词初始最多每秒5次，行/位置变化才更新；逐字强调按真实字时间边界触发，合并同帧变更，最多一次/显示帧，不把5Hz行采样当字级精度保证。无逐字动画时仍保留真实当前字或逐行可读状态；隐藏页零视觉tick，拖动直接响应手势 |
| 预取与请求 | 最多预取下一曲一份轻量元数据，同键合并，无全队列资源解析。F-059允许活动后端内部为相邻曲做有界过渡准备，字节/时间窗口须在LP-05探针冻结并计入总PSS，不新建第二活动播放器；未经测量不宣称无缝。二维码随退出停轮询 |
| 远程媒体等待 | 初始HTTP连接5秒、连续无数据读取10秒；初次/重缓冲15秒无可播放进展即给重试，不限制整首持续流时长；元数据8秒总时限另见19 |

音频缓存、导入副本和未来下载配额沿用 [02 产品默认值](02-产品需求与范围.md) 与17；图片/歌词另行计量，所有应用占用共同服从实际剩余空间预留。扫描、封面补全与播放竞争时降速或暂停非关键工作。

LP-05 连续播放源码将同一 Media3 allocator 目标设为4MiB、前向时间窗口5～15秒、启动/重缓冲1/2秒、后向音频缓冲0；[运行合同](development/LP-05-gapless-continuation.md)记录单个 successor、分配粒度超量及独立 decoder/DSP/PSS。此为待云端/设备校准的实现初值，不是已测内存或无缝支持，不取代完整进程 PSS 和实际接缝验收。

默认配置保持安静、静态、离线零请求：黑底/静态封面、系统字体、逐行歌词、常亮关闭、传输/发现/联网补全关闭。用户显式启用的主题、字体、逐字、可见歌词常亮、DSP和手机功能必须真实工作。分别测默认配置、每项启用及声明支持的组合；性能冲突列具体瓶颈和LP决定，不能把关闭功能当其正常AC。

| 冷启动到可操作首页 | P95 ≤ 3秒 | 优化发行候选30次，报P50/P95/最差；不等扫码、网络或全库扫描 |

| 控件可见反馈 | ≤ 100ms | 从有效触控/命令到达应用入口至确认收到意图的可见变化；不等同音频动作完成 |

8秒是**元数据解析总时限，不是首声承诺**。普通在线首声与触发 Meting 后的端到端首声分别统计；后者另报直连、补充解析和媒体连接/缓冲，不能混入4秒样本，也不能用8秒解析掩盖后续无限缓冲。缓冲/媒体请求的取消和超时按03/19，失败可退出。

### 数据规模分开记录

- **扫描器实机验证**：1000个独立可读的小型音频文件，记录格式、大小、目录和总占用；可用合法合成短音频，不能以1000条指向同一个文件的引用替代。与少量代表性完整曲目/大图/LRC异常样本一起覆盖播放和解析边界。
- **模型/数据库基准**：1000条受控数据库记录验证分页、分类、搜索、排序、列表持久化和内存，不必附1000首完整歌曲；此结果不能证明实体扫描通过。
- 真实完整曲库容量按设备空间和实际样本记录，不从合成记录推断所有格式或任意文件容量。F-086/T-40必须验证超过10000条的完整逻辑选择（含10000/10001边界、重复实例及多页），不要求10000首实体音频；扫描实体规模与队列规模分别记录。旧10000条活动队列硬上限撤销，不能以“缩小选择/仅播一首”替代播放全部。

## 4. 可复核的测量方法

### 产物与对照条件

全部APK与测试APK均在云端构建，本地只安装、执行设备测试和采集。当前能力和待建的 CI-01–04 见 [09](09-云端构建与本地验证.md) 与 [20](20-终审结论与开工清单.md)；CI-02须在P1性能基线和首次正式候选前补齐，现有旧发布流程不能用来先取候选。

最终发行候选为优化 Release，`debuggable=false`、`profileable=false`。需要 profileable 的工具使用独立云端诊断包及测试APK，记录对应代码、优化参数和配置差异、各自包标识/哈希；**诊断包与发行包不是同一APK，不要求或声称哈希相同**。基线和候选按相同产物类型对照，不拿Debug或诊断包与发行包混算改善。

启动、交互、首声和后台等可在发行包取得的指标须在实际发行APK复核；受权限限制的细粒度trace只能作为诊断证据，按P0冻结的兼容测量/替代判据闭环。仅诊断包通过不能自动判发行包通过。截图与发行性能测量可分轮，但绑定同一发行APK；诊断报告单独关联它。

记录同一冻结source/snapshot下的候选包组合，手表与手机分别登记build SHA、run/attempt/artifact、精确包名/版本、APK和证书SHA-256、构建参数及设备固件。跨端结果绑定实际两包、协议/schema与授权组合，不能由手表单包成绩推断手机性能。基线/候选使用同一物理设备（当前主测为Watch X2）、耳机、音量、网络、亮度、电量模式和相近温度，交替测量；手机端同样固定对照条件，充电/热降频、首次初始化、冷/热启动和缓存命中/未命中分开。

### 指标定义与统计

- “可操作首页”要明确页面和按钮可用终点，启动画面/首帧不算。冷启动指进程冷启动，磁盘与系统缓存条件注明。
- 首声终点是实际输出声音；READY、播放命令或进度变化只能作代理指标。暂停/seek也需注明实际输出检测方法；只有内部事件时对应声音验收仍未完成。
- P95使用nearest-rank，索引为 `ceil(0.95 × n)`（从1起）。保留原始样本、失败/超时/丢样本数；有限样本不代表总体保证，失败不能被悄悄排除。
- 帧周期为 `1000 / 实测刷新率Hz`，变化时分段；CPU工作时长、overrun和完整帧耗时不能互换。工具/API不支持时使用P0冻结的兼容统计或trace，注明口径，不填0；模拟器不替代真表。
- PSS使用MiB并注明进程集合/时刻，不用Java或native heap冒充。CPU/GPU、温度及扫描时长记录同条件趋势，异常需定位。

### P0 冻结耗电测量与退出条件

先在最小单播放器探针上记录可读的电量/电荷或能耗量、最小分辨率、重复波动及工具开销。按设备冻结比较场景、时长、样本与判据后再做候选验收；默认在线/本地熄屏各3组60分钟交替对照，可复用满足同条件的长测。亮屏选播放页/歌词页代表场景，时长在P0记录；后续PR只复测受影响场景。

基线消耗显著高于测量粒度且波动允许辨别差异时，计算 `(候选耗电速率－基线速率) / 基线速率`，同时报告绝对百分点/小时或实际能耗单位。整数电量两次都下降1%不能证明精确相等，零或不可分辨的基线不能作分母。

**若P0探针已证明比例不可测，当场选定并冻结可执行替代，不无限延长长测：**优先采用可分辨的绝对耗电区间/差额与由基线波动确定的容差；仍不可分辨时，冻结设备可取得的trace/资源观察项与固定持续时长，检查隐藏页面无UI周期任务、无异常持续CPU/唤醒持有、无应用引起的持续升温或停播。明确工具、观察窗口、失败条件及剩余测量限制；不能只写“耗电正常”。必要的解码和缓冲不当作异常，诊断开销单列，发行APK完成同条件持续播放复核。

报告只能写“按已冻结替代标准通过，20%比例未验证”，不可写“20%已达标”。若连冻结的替代证据也采不到，相关验收保持未测并明确缺口；不通过换表头、填0或追加无限等待来放行。

### 回归判定

超过冻结标准、ANR、应用侧停播、泄漏或无界增长先修复。可分辨的关键耗时/PSS/耗电相对基线恶化超过10%时，再做两组同条件对照；确认回归后优化或回退。低于分辨率的指标按已冻结绝对容差或替代判据判断，不计算虚假百分比。不用新基线覆盖失败，必要取舍须有所有者的证据化决定。

失败、撤权、取消、恢复路径也纳入受影响场景。新增T-41–56覆盖后端切换/回退、DSP输出、额外解码和无缝、原件操作、配套会话、主题字体与常亮/逐字；对应256原AC仍须逐项留证。手表与配套端分别记录PSS/CPU/包体/后台网络，不以只测手表忽略手机常驻开销。填写 [性能记录](templates/性能验收记录.md)，保留脱敏样本、trace和结论；文档PR只做文本核对，不制造设备数据。
