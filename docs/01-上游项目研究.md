# 上游项目研究

状态：静态代码审阅完成；未构建上游、未调用真实账号接口、未做手表实测。证据编号对应 [08 研究来源与决策记录](08-研究来源与决策记录.md)。

## 1. 研究结论

建议建立独立的 MeloX Watch 工程，以 Android 版的 Kotlin 业务逻辑为主要代码来源，以原项目的 Apple Watch 功能和页面组织为产品参考。首版在线平台为网易云，另包含用户文件本地库及用户可选Meting解析；使用手表自己的音频输出，在线路径才需要网络。

原因是 Android 版已有 Media3、网易云接口和歌词解析，但主要逻辑仍集中在手机 `:app` 模块；其播放服务直接依赖手机 Activity、设置页面、局域网、多音源和厂商通知。Apple Watch 版已经缩减功能范围，但 SwiftUI、AVFoundation、WatchConnectivity 不能直接用于 Android。[A02][A03][A05][B02][B03][B05]

## 4. 阅读代码后发现的差异

### 4.1 构建声明不能只看 README

Android README 写的是 Android 8/API 26、Gradle 9.5.0；实际 `app/build.gradle.kts` 中 `minSdk=24`、`compileSdk=37`、`targetSdk=37`，wrapper 指向 Gradle 9.5.1。构建脚本声明 AGP 9.3.0、Kotlin 2.3.21、Compose BOM 2026.06.00 和 Media3 1.10.1。[A01][A02]

这些只是上游此提交的配置，未验证它们在本机可下载或构建。本计划不将其直接认定为手表工程的推荐稳定组合。P0 根据实机 API 与依赖最低要求选择并锁定组合，初始 `minSdk` 候选为 26；若设备低于它，单独评估降级成本。

### 4.2 provider 声明不等于完整接口实现

`NeteaseProvider` 列出 Library、Playlists 等多项能力，但其类实际实现的接口主要是 Search、Lyrics、Playback、LocalAggregation；部分功能仍通过原生 `Netease*Client` 完成。搜索实现对 `page > 1` 返回空结果。继续向下核对后，`NeteaseSearchClient.searchSongs` 固定 `offset=0`；`NeteaseUniversalSearchClient.searchMedia` 同样固定 `offset=0`，并对 Songs 类型直接返回空列表，因此不能简单切换到后者就得到歌曲分页。[A03][A04]

因此手表端需要自己的窄接口适配器，并明确增加真实分页；不能根据能力枚举自动展示全部入口，也不能把“第一页有 30 条”当成分页已实现。

搜索还依赖 `MeloXHotRules`/`MeloXHotScripts`，音质客户端依赖远程兼容策略。提取时应把这些可选行为改为显式注入的策略，首发使用已说明的本地策略，避免为了复用搜索而引入完整远程脚本体系；正常 EAPI/WEAPI 请求协议仍需保留并独立验证。[A04][A07]

### 4.3 二维码登录存在两条不同路径

Android 的 `NeteaseQrBridge` 让 WebView 内的页面申请 key 并轮询，代码注释记录了原生请求和桥接在风控、页面加载上的问题；Apple Watch 通过 EAPI 直接请求二维码 key 与登录状态，使用的参数也不同。[A06][B04]

计划先验证无 WebView 的原生二维码链路，再根据实测选择方案。若原生链路受阻且手表 WebView 可用，评估移植 Android 网页桥接；若两者均失败，独立登录里程碑暂停，先确定手机辅助登录的新增范围。不要假设原生二维码已在 Watch X2 上可用。

### 4.4 播放服务不是可直接依赖的公共模块

`MeloXPlaybackService` 导入 `MainActivity`、手机设置、UI 层歌词加载器、LAN、多音源、HyperOS 和 vivo 通知适配，还包含多播放器相关逻辑。[A05]

手表版采用新的服务组织方式，逐项迁移音频焦点、耳机断开、队列恢复等必要行为。AutoMix、USB 独占、手机厂商通知、悬浮窗和动态插件均不进入首发依赖图。

### 4.5 下载必须单独定义权限与状态

`NeteaseQualityClient.downloadSourceBlocking()` 在下载接口失败后可能回退到播放资源；`MeloXProviderDownloadStore` 使用自己的任务/索引逻辑并含 Compose 状态依赖。[A07][A09]

手表方案需要分别表达“能播放”和“允许下载”，保留资源有效期与实际音质。是否保留上游下载回退行为，在 P4 接口验证后明确；默认不因获得播放 URL 就自动认定有下载能力。

## 5. Apple Watch 版值得参考的部分

| 文件/目录 | 本次确认的行为 | 对 Android 手表的价值 |
| --- | --- | --- |
| `MeloXWatch/Root/WatchRootView.swift` | 横向三页：队列、正在播放、歌词；菜单单独进入 | 能形成清晰的圆屏主流程，但位置尺寸需重做 |
| `MeloXWatch/Account/WatchQRLoginView.swift` | 生成、等待扫码、等待确认、过期、成功、失败状态 | 直接作为登录验收场景来源 |
| `MeloXWatch/Networking/WatchNeteaseAPI.swift` | 搜索、日推、账户、歌单、详情、播放 URL、歌词、QR | 可作为最小 API 范围参考 |
| `MeloXWatch/Playback/WatchPlaybackStore.swift` | 队列、随机/循环、上一首行为、进度和会话恢复 | 参考产品语义，测试需在 Kotlin 端重建 |
| `MeloXWatch/Playback/WatchAudioPlaybackEngine.swift` | 远程资源先下载到临时文件，使用 AVAudioPlayer；卸载资源时删除临时文件 | 说明其“本地播放”不等于持久下载库；Android 使用流式播放与独立离线库 |
| `MeloXWatch/Connectivity/WatchConnectivityStore.swift` 与 `MeloXWatchShared/` | 通过 WCSession 发送/接收账号和快照消息 | 参考消息分类；传输机制、存储方式不能直接照搬 |

依据：[B02]–[B06]。本次所读同步模型的核心是账号快照，不能据此宣称已有完整的手机远程播放器协议；局域网控制另参考 Android 的 LAN 文档。

## 6. 范围裁剪和来源记录

首发提取网易云网络逻辑、歌曲模型、LRC 解析及必要播放语义。只在验证后扩展 YRC/TTML、下载和协同。多平台自动替代音源、QuickJS 插件、ONNX/识曲、OpenJTalk、AutoMix、重型歌词特效、DLNA/PCM 投放留在范围外。[A01][A02][A05]

本节描述原始研究的裁剪依据；后续用户确认的首版还包含17的完整本地音乐和19的自填Meting解析服务，固定源码仍以锁文件为准。最终功能/工期与开工顺序以02/05/20为准，不按历史“首发提取”段落遗漏新增范围。

两个根 `LICENSE` 都是 GPLv3 文本，部分资源有独立说明；例如 Android 的 SF Pro 字体说明明确它不受项目 GPL 覆盖，原项目 README 单独说明 PV Tool 的许可。[A12][B01][B07] 后续复用代码时记录来源与修改，发行时整理相应许可证、源码及构建说明。手表 UI 优先使用系统字体和来源清楚的图标，首发不搬这些字体和 PV 资源。
